# index：知识库入口与使用说明

> 覆盖 `web/docs/agents/` ｜ 核对 2026-10-11

## 功能介绍

这是 `web/`（浏览器侧前端）知识库的**入口文件**。知识库只做两件事：**把 AI 送到该读的文件**、**统一开发风格**；它不是代码的事实源。

读法三步：

1. 在这里判断问题属于**哪一层 / 哪一页**，拿到对应文档；
2. 进该文档的**索引**节，定位到具体文件；
3. **打开源码交叉验证**——结论一律以源码为准。

本知识库按「父级只描述当前层级、子级靠对子级的索引引导」组织：`index.md`（本篇）只说明顶层有哪些层、每层归哪篇文档、页面入口；各层内部由该层文档展开，页面内部由该页文档展开。

**路径约定**：本文档与各分层文档中的路径一律**仓库根相对**，以 `web/` 或 `bangumi/` 开头（例：`web/src/page/mainPage/index.tsx`、`bangumi/src/web/protocol.ts`）。不写 `src/...`，也不写 `styles/frame.css` 这类裸相对路径。

## 规则

**1. 知识库不是事实源。**

- **规则**：知识库只用于定位；把知识库作为依据时，必须到真实源码中交叉验证。
- **为什么**：文档会滞后、会写错、会与源码不一致；它给的是路径与线索，不是结论。
- **后果**：拿过期描述当依据，会直接改错地方，而且错误会被「文档就是这么写的」掩盖，事后极难发现。

**2. 修改代码后一定同步更新知识库。**

- **规则**：完整完成开发任务之后，先给出**知识库更新方案**（改哪几篇、改哪些条目），经用户确认后再修改文档。
- **为什么**：知识库一旦与源码脱节就不可信，比没有知识库更糟。
- **后果**：下一次对话按过期文档改错地方。

## 写作规范

新增或修改本知识库的文档时遵守以下约定；这一节是文档风格与内容的事实源。以下条款约束 `web/docs/agents/` 下的层文档；`web/AGENTS.md` 是项目入口文档，结构由它自身承担，不受第 1 条约束。

### 文档结构

**1. 每篇固定三段结构。**

- **规则**：按固定顺序写：`# <标识>：<中文层名>` → 一行元数据头 → `## 功能介绍` → `## 索引` → `## 规则`；文件多时在 `## 索引` 下按子目录分 `###` 组；有废弃路径时在末尾追加 `## 不要去找的旧路径`（见第 5 条）。元数据头形如 `` > 覆盖 `web/src/<目录>/` ｜ 核对 YYYY-MM-DD ``，「核对」是最后一次对着源码验证的日期。
- **为什么**：结构固定后，读者可以按位置跳读，不必通读全篇；元数据头让「这篇有多可信、覆盖到哪」一眼可见。
- **后果**：各篇结构不一致时，读者只能通读才能找到文件清单；元数据头缺失时，也无从判断这篇覆盖到哪、是否还新鲜。

**2. 不写会漂移的数字。**

- **规则**：不写行数、文件个数、条目数量这类会随代码变动的数字；必须写时补「截至 YYYY-MM-DD」。有穷尽类型守卫兜住的数量（如 `ContentKind` 的成员数）不在此列——它们改错会编译失败。
- **为什么**：这类数字没有任何机制保证同步，读者也无从判断它是否仍然成立。
- **后果**：一个过期数字会让读者连带怀疑同一行里本来正确的描述。

### 路径与引用

**3. 路径一律仓库根相对。**

- **规则**：写成 `web/src/...` 或 `bangumi/...`，不写 `src/...`，不写 `styles/frame.css` 这类裸相对路径；路径一律放进反引号，便于脚本抽取校验。例外只有两类：索引表「文件」列里的层内文件名（如 `color/bgm.css`）与层名（如 `components/`），它们的基准由所在列与语境给出。
- **为什么**：知识库文档被单独打开时没有「当前目录」这一上下文，裸路径的基准只能靠猜。
- **后果**：按错基准找文件会得出「文件不存在」的错误结论，或改到同名但不相干的文件上。

**4. 文档之间用 Markdown 链接。**

- **规则**：引用另一篇文档时写 `[components.md](components.md)`，不要只写反引号里的文件名。
- **为什么**：反引号是纯文本，链接既可直接打开，也可被脚本解析出引用关系。
- **后果**：只写文件名时，文档改名或移动不会有任何地方报错，引用静默失效，读者按名字去找会落空。

**5. 废弃路径集中成节。**

- **规则**：已不存在的旧路径统一放进 `## 不要去找的旧路径` 小节，逐条说明「现在的对应物是什么」。
- **为什么**：旧路径混在规则正文里时与真路径外形相同，抽取路径的工具会把它们当成候选。
- **后果**：误判「文件丢了」，或按旧路径新建一份重复实现。

### 规则怎么写

**6. 只写跨文件、跨模块的约束。**

- **规则**：写成规则的内容必须**跨文件或跨模块**才成立——它约束的是层与层、模块与模块之间的契约，或者「某种写法在本层内一律不许出现」。只约束单个文件内部实现选择的，写进该文件的源码注释，不进规则。正例：「组件不读 store」约束整个 `web/src/components/`；反例：「折叠用 `hidden="until-found"`」只约束一个 hook 的实现方式，归 `web/src/components/conversation/ProcessRows.tsx` 的注释。
- **为什么**：规则节的读者是「准备改这一层的人」，问的是「我改这一层要守什么」；单文件实现选择只有打开那个文件时才有意义，放在层文档里既占篇幅又找不到归属。
- **后果**：实现细节混进规则后，层级变得参差，读者无法从标题判断哪条是硬边界、哪条只是某个文件的写法偏好，跨层约束因此被稀释。

**7. 规则按约束性质分组，类别按需取用。**

- **规则**：规则节按约束的**性质**分组，每组一个小标题。组名从下表取用；某一层有哪几类就写哪几组，**没有的不写，也不为齐整硬凑**；表里没有的，按同样的命名风格新增——组名描述「约束了什么」，不描述「改哪个文件」。
- **为什么**：类别是读者找规则的索引，扫一眼组名就知道这一层有没有自己要找的那类约束。类别开放而不固定，是因为各层的约束构成本来就不同：`web/src/types/` 只有引用方向与真相源，`web/src/router/` 才会出现状态归属与失败降级。组名统一用词，跨层对比同一类约束才成为可能。
- **后果**：不分组时规则只是一条条并列，读者必须逐条读完才知道有没有相关内容；把类别写死成固定几类，则会逼着人把归不进类的条目硬塞进某一组，或者为了凑齐类别写出没必要的规则——两种情况都会让规则节重新变得不可信。

**可用类别**（参考池，按需取用）

| 类别 | 收什么 |
|---|---|
| 引用方向 | 谁能 import 谁，哪些逆向引用被禁止 |
| 单一真相源 | 某个值 / 表 / 类型 / 文案只有一处定义，其余地方引用它 |
| 归位与命名 | 新增文件、令牌、类型该进哪一层哪一目录；类名前缀怎么分区 |
| 模块边界 | 层与层、前端与宿主之间的职责划分 |
| 副作用位置 | 请求、落盘、读时间只允许出现在哪里 |
| 状态归属 | 哪类状态放 URL、store 还是组件内部 |
| 改动联动 | 动一处必须同改哪几处，含两处必须同时改的同步要求 |
| 顺序契约 | 有先后依赖的清单，顺序本身就是约束 |
| 失败与降级 | 数据缺失、非法、出错时的行为约定 |
| 穷尽性守卫 | 用类型或断言让漏登记直接编译失败 |
| 技术边界 | 明确不引入什么（框架、库、模式） |
| 产物边界 | 什么代码不许进产物 |

> `index.md` 的规则节写**元规则**（知识库自身怎么用），不适用本池。

**8. 一条一事，能合就合。**

- **规则**：一条规则只讲一件事，标题就是结论；同一主题下能合并的合并，不为显得完整而拆条；索引表「含义」列已经说过的内容不重复；给不出「后果」的条目改写成「功能介绍」里的描述，不写成规则。
- **为什么**：规则越接近「一件事」，越容易在动手改代码前被扫到；拆得太碎或与索引重复，读者会直接跳过整节。
- **后果**：条目碎而不齐后，规则节被当成装饰，改代码时不再有人查它。

**9. 每条规则写足三段。**

- **规则**：每条规则写「规则 / 为什么 / 后果」三条。「规则」写约束本身与适用范围，「为什么」写设计意图与它挡掉的问题，「后果」写违反后的具体现象（不是「会出问题」这类空话）。
- **为什么**：三段分别回答「要守什么」「为什么有这条」「不守会怎样」；缺任一段，读者都无法判断这条约束的边界与分量。
- **后果**：缺「后果」的规则在改代码时不会被遵守，约束形同不存在。
