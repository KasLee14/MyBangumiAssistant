Bangumi 助手内容组件库

12 个用于多样化消息展示的 React 组件。宿主当前只下发 header / user / assistant / notice / error / activity / confirmation，这些内容条目是协议里 已经预留、浏览器侧已经能渲染的能力；宿主只要按下面的结构下发，界面立刻生效。

契约：bangumi/src/web/protocol.ts（唯一类型来源，本页每节的「数据结构」都从它逐字摘录）· 组件：web/src/components/content/ · 样式：web/src/styles/content.css

0. 这个库解决什么 以及宿主怎么启用

解决的问题

纯文本回答在「列表 / 分布 / 对照 / 原始输出」这四类内容上都很吃力：搜索结果堆成一段文字不好扫， 收藏统计说成「7 分 12 部、8 分 44 部…」不如一排柱子，写入结果说成「已把评分从 7 改成 8」不如一张前后对照表。 这 12 个组件把这些结构从模型文本里拿出来，交给界面渲染：

  • 看得快：封面墙、条形、章节网格、前后对照各自用最适合的编码方式。
  • 可核对：数字用等宽字体、原始输出保真不截断、修改前后并排可辨。
  • 不改前端就能上线：宿主换个 kind 即可，浏览器不需要再发版。

宿主如何启用

  1. 在 SSE 帧的 items 里追加一条内容条目（或全量帧里带上它）： { id, version, kind: 'subjects', subjects: { … } }。 不需要改 TranscriptItemView，也不需要前端发版——12 个 kind 已经在协议联合类型里， ContentItem 按 kind 分派。
  2. 在 TurnView / 轮次分组那一侧把内容条目当作正文条目渲染： <ContentItem item={item} />（item 的类型是 ContentItemView）。这一步属于接入动作，不在本库范围内。
  3. id 用会话内唯一且递增的条目号；version 在被原地更新（例如进度 11 → 12）时递增。 浏览器按 id 替换、按 version 判断是否需要重发，不会重复追加。
  4. 未知 kind 会被安全忽略（渲染为 null），所以宿主可以灰度：先只发 subjects， 其余留到后面。
需要你决定的一件事：内容条目与文本回答混排的粒度。建议「一轮正文里最多 1–2 个内容条目 + 一段说明文字」， 内容条目承担结构、文本承担结论；否则会话流会变成卡片瀑布。

属性与令牌

组件只消费下面这批令牌（由 web/src/styles/bgm.css 提供；界面只有浅色一套外观）。 content.css 里没有写死颜色，全部走令牌：

本库相对原型的取舍
  • 不用 hover 承载信息（交互文档 §13 明确要求规避）：章节状态、标签计数、链接 hint、修改前后都常驻可见。
  • 标签是纯展示：用 span 而不是 button，不可点就不装作可点。
  • 数字一律等宽：评分、进度、计数、章节号，位数对齐才好扫。
  • 表格与画廊不隐藏滚动条：横向溢出用滚动条本身说明「还有内容」。
  • 图片 loading="lazy" + 失败回落：占位块与图片同尺寸，卡片不跳版。

数据结构 · protocol.ts

export type SubjectKind = 'book' | 'anime' | 'music' | 'game' | 'real';
/** 单个条目卡；可直接由 `get_subject_details` 的结果映射。 */
export interface SubjectCardView {
  id: number;
  /** 原名。 */
  name: string;
  /** 中文名；缺失时界面回落显示 `name`。 */
  nameCn?: string;
  kind: SubjectKind;
  /** 封面图地址；缺失时显示占位块。 */
  image?: string;
  /** 全站评分（0–10）。 */
  score?: number;
  /** 评分人数。 */
  scoreCount?: number;
  /** 站内排名。 */
  rank?: number;
  /** 放送/发售日期，已格式化的文本。 */
  date?: string;
  /** 简介；界面按行数截断。 */
  summary?: string;
  /** 标签名，可带收藏人数（界面只显示名字与可选计数）。 */
  tags?: string[];
  /** 条目页地址。 */
  url?: string;
}
/** 条目网格或列表；`layout` 决定封面墙还是紧凑行。 */
export interface SubjectCollectionView {
  title?: string;
  items: SubjectCardView[];
  layout: 'grid' | 'list';
  /** 结果总数；大于 `items.length` 时界面提示还有更多。 */
  total?: number;
  hint?: string;
}

接入说明

  • 数据从哪来：search_subjects / browse_subjects → layout: 'grid'（浏览、候选）；get_user_collections / get_index_subjects / get_subject_relations → layout: 'list'（核对、清单）。
  • 必填：items[].id、items[].name、items[].kind、layout。
  • 可选：title、total、hint，以及卡片上的 nameCn / image / score / scoreCount / rank / date / summary / tags / url。
  • kind 映射：Bangumi 的 subjectType 1/2/3/4/6 → book/anime/music/game/real，宿主侧统一映射一次，浏览器不再判断数字。
  • total 与分页：工具的 page.total 是真实总数、data 是本页条目。把 total 原样带上，界面才会在末尾提示「还有 N 条未展示」；只发本页数字会被读成总数。
  • 缺失值：没有评分就不要填 0（0 分是合法评分），字段直接省略；image 缺失或加载失败都会回落成同尺寸占位块。
  • 单位与格式：score 是 0–10 的数值（界面保留一位小数），scoreCount/rank 是整数，date 是已格式化的文本。

数据结构 · protocol.ts

/** 统计数据的一项。 */
export interface StatEntryView {
  label: string;
  value: string;
  /** 相对量（0–1），用于条形长度；缺失时只显示数字。 */
  ratio?: number;
  hint?: string;
  tone?: 'default' | 'primary' | 'muted';
}
/** 统计卡：一个主数字 + 一组分布。 */
export interface StatsView {
  title?: string;
  /** 主数字，例如平均分。 */
  headline?: { value: string; label: string };
  entries: StatEntryView[];
  /** `bars` 横向条形；`histogram` 竖向柱状（评分分布）；`list` 纯列表。 */
  mode: 'list' | 'bars' | 'histogram';
  note?: string;
}

接入说明

  • 数据从哪来：get_user_collections 的本地聚合（评分分布、收藏状态分布）、get_subject_details 的 ratingDistribution（全站评分分布）。
  • 必填：entries[].label、entries[].value（字符串，单位由宿主写进文本，界面不换算）、mode。
  • 可选：title、headline、note、entries[].ratio、entries[].hint、entries[].tone。
  • ratio 怎么算：0–1 的相对量，柱长 = ratio × 100%。用「该项人数 ÷ 最大项人数」或「该项人数 ÷ 总人数」都可以，但同一张卡里要用同一种口径；越界值会被夹到 0–1，不会出现 NaN 宽度。
  • mode 选择：histogram 用于 1–10 分这类等距分档（按传入顺序渲染，站点原型是 10→1）；bars 用于不等距项（收藏状态、标签 Top N）；list 用于平均值、计数这类不构成分布的数据。
  • tone：default 弱灰柱、primary 主色柱、muted 更弱的灰柱（例如「未评分」「1 分」这类空档）。headline 只用于一个主数字。

/** 进度：数值进度条或章节网格。 */
export interface ProgressView {
  title?: string;
  current?: number;

接入说明

  • 数据从哪来：get_user_episode_collection（章节列表 + 个人状态）→ 数值进度与 episodes；get_single_episode_collection（单章节）→ 只给 episodes 一项；get_user_subject_collection 的 ep_status/vol_status 与 totalEpisodes/totalVolumes → current/total。
  • 必填：无。数值进度、章节网格、note 都是可选的，但至少要有一项，否则界面显示「没有可展示的进度」。
  • 可选：title、current、total、unit、episodes、note。
  • current / total 必须成对：只给一个不画进度条（避免「12 / ?」这种半截信息）；total 为 0 也不画，防止除零。
  • unit：动画写「话」、书籍写「卷」或「章」，会作为文本后缀出现在「12 / 28 话」里，同时用于进度条的 aria-label。
  • episodes[].state：done（已看：主色浅底 + 主色描边）/ current（当前：主色实心）/ todo（未看：弱文本）。Bangumi 的章节收藏码是 0 未收藏 / 1 想看 / 2 看过 / 3 抛弃，映射时「抛弃」应归到 todo，不要混进 done。
  • label 是字符串：章节号请宿主补齐两位（01…12），界面不补零、不按数字排序。
  • 注意分页：章节接口默认每页 100 条。只发一页时请在 note 里说明，别让网格看起来像全部章节。

11. callout 三段式提示 Callout.tsx

示例 progress / success / warning / error
· 正在提交评分 8 分… 进行中
✓ 已提交评分 8 分，并独立回读确认。 成功
△ 已提交，但回读结果与预期不一致，请核对。 注意

期望 rating=8，回读得到 rating=7；可能是站点缓存，稍后可再核对一次。

× 提交失败：连接 bgm.tv 超时。 失败

错误码 NETWORK_TIMEOUT · 未发生写入，可以安全重试。

数据结构 · protocol.ts

/** 三段式反馈（进行中 / 成功 / 警告 / 失败）。 */
export interface CalloutView {
  tone: 'progress' | 'success' | 'warning' | 'error';
  text: string;
  detail?: string;
}

示例 JSON

{
  "id": 22,
  "version": 4,
  "kind": "callout",
  "callout": {
    "tone": "success",
    "text": "已提交评分 8 分，并独立回读确认。",
    "detail": "回读时间 2024-10-28 21:04；如需撤销，可以再说一次原来的分值。"
  }
}

接入说明

  • 数据从哪来：工具调用的阶段状态——写入前的「正在保存…」、提交后的「已提交，等待回读核对」、校验失败的 SchemaInputError、网络超时的 AppError。
  • 必填：tone、text。
  • 可选：detail（更小字号的补充，比如错误码、下一步建议）。
  • 与现有 kind 的分工：error / notice 是纯文本行，适合整轮失败；callout 是带语义色与状态词的结构化提示，适合工具结果里的阶段反馈。同一件事不要既发 notice 又发 callout。
  • tone 的口径：progress 蓝（进行中）、success 绿（已确认完成）、warning 黄（部分成功 / 需用户决定）、error 红（失败）。不要用 success 表示「已提交但未回读」，那属于 progress 或 warning。
  • 文案稳定：状态词由界面固定（进行中/成功/注意/失败），宿主的 text 保持稳定措辞，不用随机语气词，避免宽度跳动。
  • 播报：组件带 role="status"，插入会话流时读屏器会主动播报，所以不要把它用在会高频替换的条目上；更新场景请递增 version，不要新发条目。
