## 1. 本次故障结论与证据

以下为自动代理实施前的初次诊断快照；当前默认行为已改为自动发现，不能再将表中的 `proxy=null` 视为当前状态。

截图中的公开搜索失败来自 Bangumi 网络连接层，而不是缺少登录。登录缺失同时存在，但它没有阻止公开搜索的权限含义。

| 核对项 | 实际结果 | 能证明的范围 |
| --- | --- | --- |
| 原会话 `53353040-0e8b-4105-aedb-736e76658929` | `search_subjects` 先搜 `muv luv`，再搜 `Muv-Luv`；两次均为 `BGM_NETWORK`，分别约10.9秒 | 原错误是请求未能连接，不是 HTTP 401/403，也不是没有候选 |
| `npm start -- login-status` | `saved=false`、`networkChecked=false` | 本应用未保存登录；不读取旧 bgm-cli 登录或日常浏览器凭据 |
| 当前应用配置 | 用户配置文件不存在，`BANGUMI_AGENT_PROXY` 未设置，有效 `proxy=null` | 当前应用走默认直连；其他通用代理环境变量不被此请求链路自动采用 |
| 同路径匿名请求直连 | 约10.7秒后 `UND_ERR_CONNECT_TIMEOUT` | 当前环境对 `next.bgm.tv` 的直连发生连接超时；不能进一步断定 ISP、DNS 或路由中的具体设备故障 |
| 同路径匿名请求使用 Clash `http://127.0.0.1:7890` | HTTP 200，约0.6秒，4条候选 | 不登录也可完成本次公开搜索；指定代理可解决当前连接问题 |
| 实际 `BgmReadClient` / `read-worker` 临时指定 Clash | 未登录时正常返回4条候选，包括 Muv-Luv Alternative 第二季 | 生产查询桥接及结果转换在此匿名场景可用；不是仅用另一套 HTTP 客户端成功 |

请求固定为 `/p1/search/subjects?limit=5&offset=0`，正文为 `keyword=muv luv`、`sort=match`、`filter.type=[2]`。搜索使用 POST 读取资料，没有账户修改。代理仅作为验证调用的参数，没有保存用户配置、改变系统代理或进行登录。

原日志不保留底层连接原因，因此历史两次失败的底层子错误不能追溯到具体 socket。当前直连复测、失败耗时以及同路径代理成功，共同支持“未启用应用代理导致直连失败”的结论；不将当前复测冒充历史底层日志。

### 出错与重试的代码位置

- `src/config/config.ts`：没有用户配置时代理默认关闭；显式 `config.proxy` 优先于 `BANGUMI_AGENT_PROXY`。
- `src/cli/main.ts`、`src/adapters/bgm-cli/client.ts`：将应用代理传入子进程的 `BGM_PROXY`。
- `src/adapters/bangumi-web/transport.ts`：代理非空才创建 `ProxyAgent`；网络异常归为 `BGM_NETWORK`，无自动网络重试。
- `src/adapters/bgm-cli/errors.ts`：桥接输出的 `BGM_NETWORK` 被转成“账户、权限或网络”的笼统消息，丢失了可行动的提示。
- `src/core/agent.ts`：工具失败后仍继续模型循环，本轮没有确定性的失败停止策略；本次换词重试由模型发起。
- `src/cli/chat-controller.ts`：已有 `/login` 和认证失败更新登录卡片，但工具失败不能直接结束本轮并交还登录引导。

## 2. 回退目标与能力划分

用户要求：需要 Bangumi 登录的功能在未登录或认证失效时，直接进入登录引导，不继续无意义的重试。工程实施还应区分网络与权限，避免把公开查询故障误导成登录问题。

| 能力 | 未登录时行为 |
| --- | --- |
| 公开搜索、公开详情、公开章节资料、助手使用咨询 | 继续提供；网络失败给网络回退。受限条目依实际响应处理，不能承诺匿名可读所有内容 |
| 本人收藏、本人进度、包含个人状态的查询 | 本机认证缺失时在相关读取前停止，显示登录引导 |
| 收藏/进度/删除预览与执行 | 在账户及现状读取前检查登录；缺失时不给写入授权，不执行或确认旧预览 |
| 基于个人收藏的推荐 | 需要登录且需要实际可用的收藏能力；登录不能补齐尚未实现的全历史或 M5 工具 |

只检查最终所用能力，不把所有自然语言请求都锁在登录后。现有范围分类只做任务分流；认证和写入权限继续由确定性宿主代码判断。

## 3. 分层实施建议

### 3.1 统一失败分类

保留底层错误码，增加确定性的宿主回退类别和下一步操作，供 `ask`、交互 chat、普通文本 chat 与独立命令共同使用。不把凭据、原始响应体、动态令牌或模型思考纳入错误元数据。

| 分类 | 判定依据 | 固定处理 |
| --- | --- | --- |
| 需要登录 | 无本机登录、明确过期、`WEB_AUTH_REQUIRED`、`WEB_AUTH_INVALID`、`BGM_AUTH_REQUIRED`、HTTP 401 | 停止相关能力，进入登录引导；停止本轮模型工具重试 |
| 账户改变 | 数字账户不一致 | 旧预览与授权失效，引导重新登录及核对账户 |
| 凭据存储异常 | `WEB_AUTH_STORAGE` 等本地读取/解密失败 | 明确本机登录无法读取，提供重新登录入口；不宣称网站已判定认证失效，不自动删除文件 |
| 网络连接失败/超时 | `BGM_NETWORK`、`BGM_TIMEOUT` | 停止本轮 Bangumi 业务调用，提示应用代理/连接诊断；登录状态保持未核实，不清除登录 |
| 权限不足 | HTTP 403 | 明确资源受限，不承诺重新登录就能解决，不换关键词重试 |
| 限流/服务异常 | HTTP 429/5xx | 提示稍后由用户再试，当前轮结束；不自动重发 |
| 资源不存在/解析失败 | HTTP 404、`INVALID_RESPONSE` | 给出对应原因；404 不等于未收藏，非 JSON 不等于未登录 |
| 取消 | `CANCELLED` | 沿用取消结果；已提交写入先完成独立回读 |

只有固定域、固定认证路径且有明确证据的登录跳转才归为需要登录；一般 3xx、403、HTML 页面或验证码页面不直接认定为账号未登录。登录浏览器失败也沿用上述区分。

底层连接原因可保存为白名单诊断子码（例如 `UND_ERR_CONNECT_TIMEOUT`），附安全的目标主机、是否启用代理、阶段和耗时。不能直接输出原始异常、headers、Cookie 或 URL 查询内容。

### 3.2 登录前置检查

- 在共享领域工具/账户适配入口设置认证守卫，覆盖自然语言模型工具、宿主直接处理的单项修改、预览/确认以及独立 CLI。不能只修改 chat 顶部卡片或系统提示词。
- 缺少本机认证时本地返回，不调用 `/p1/me`，也不先调用 `get_progress` 中不必要的作品读取。无账户公开查询仍放行。
- 有本机认证仅代表可尝试认证请求；在线401再触发登录回退。既有账户一致性和写入前现状核对保持有效，界面状态不能充当长期授权。
- 本机损坏凭据不能静默忽略后继续个人操作。公开匿名能力是否临时绕开损坏凭据属于后续实现选择，本轮不默认删除或替换凭据。

### 3.3 宿主停止工具重试

- 查询阶段出现需要登录、账户改变、网络故障等终止类别后，立即结束本轮业务工具循环，输出宿主固定回退，不再请求模型决定是否换关键词、换工具或自动登录。
- 一个模型回复携带多个工具调用时，尚未执行的依赖/账户请求标记为未开始；补齐与调用ID对应的结构化结果，避免会话恢复时形成不完整的工具协议。
- 清除未完成修改及旧确认授权，保留已核实公开候选和已有执行结果。不能丢弃操作日志中的成功、失败和未知。
- 模型工具链与宿主直接操作都走同一回退规则；不新增一个可绕过权限的“自动重登工具”。
- 写请求已发送时，不能因为登录/网络回退而取消独立回读或再次提交。先由原执行器报告成功、失败、未知和未开始，再显示登录/网络引导；未知项下一轮仍先核查。

### 3.4 用户看到的回退

未登录且请求本人收藏/进度或修改：

> 此功能需要登录 Bangumi。当前未登录，本次操作未执行。
>
> 输入 `/login`，在专用浏览器中完成登录；登录后重新发送这条请求。

认证过期：

> Bangumi 登录已失效，本次操作未执行。输入 `/login` 重新登录。

以上“未执行”只适用于没有发送写入的情形。已开始写入时显示真实逐项结果及待核查项，不能统一声称没有执行。

本次公开搜索场景：

> 无法连接 Bangumi，搜索未完成。本次公开搜索不需要登录。
>
> 当前应用未启用代理；请检查 Clash 7890，并按提示设置应用代理后再试。本轮已停止，没有继续换关键词重试。

实际网络提示根据有效配置生成：已设置代理时显示“已配置代理，请检查代理连接”，不固定声称代理关闭。诊断不自动改变代理设置。

- chat 保留现有 `/login` 入口和登录菜单；用户主动选择入口后进入已有专用浏览器流程，核对网页/p1账户并保存。失败或取消保留旧凭据。
- 非交互 `ask` 和独立命令显示 `npm start -- login`；不会自动启动浏览器，`--json` 输出结构化回退类别及下一步。
- 登录成功更新卡片，让用户重新提交原请求。首版不自动恢复修改；重新读取账户和现状、重新判定权限，复杂操作重新预览确认。旧账户授权不能转交新账户。
- 不将登录失败与网络失败写成任务越界；返回字段与现有 `boundary.code` 分开，现有任务范围和混合请求的权限规则保持有效。

## 4. 当前可用的网络配置方法

后续已按用户授权实现自动发现：省略应用 `proxy` 时自动读取标准代理环境，其次读取 Windows 当前用户固定系统代理；本机匿名搜索已成功，不再要求设置应用专用变量。显式 `proxy: null` 仍表示关闭自动发现。详细规则见 [README](../README.md)；以下命令保留为手动覆盖方式。

在启动 chat 的 PowerShell 中设置应用识别的变量：

```powershell
$env:BANGUMI_AGENT_PROXY = 'http://127.0.0.1:7890'
npm start -- chat
```

若配置文件未显式设置 `proxy`，此变量优先于标准环境与系统自动发现。若配置文件显式设置 `proxy`（包括 `null`），该字段优先，需要修改该字段才能改变有效代理。此设置影响新启动的应用进程，需要退出旧 chat 再启动，不会更新已运行实例。应用模型和 Bangumi 桥接均使用同一代理配置。

## 5. 实施边界与验收

建议依次落实：错误分类及安全提示 → 共享认证守卫 → 宿主本轮停止策略 → 多种 CLI/renderer 引导 → 文档与回归。优先用现有模块与小型共享规则完成，不引入全局事件框架或通用请求权限。

必要离线验收：

1. 未登录查本人收藏/进度/修改直接得到登录引导；不调用账户请求或写入器，不能使用旧 bgm-cli 认证绕过。
2. 未登录公开搜索和详情仍可成功；网络失败没有登录误导，同轮同关键词/换关键词/换工具均不能再次请求 Bangumi。
3. 401进入重新登录引导，403保持权限提示，429/5xx停止本轮；连接失败不清除已保存登录，损坏存储与网站失效区分。
4. 模型同批多个工具调用及宿主明确单项修改都遵守守卫；错误结果、跳过结果和固定回答可完整恢复，无旧确认授权。
5. `/login` 成功、取消、失败和账户切换更新一致；登录后无自动写入，用户重提请求后重新核对和判权。
6. 已提交写入后网络/认证异常仍完成独立回读，保留未知及部分结果，不重复提交。
7. Ink、普通文本、`ask --json`、独立 CLI 输出一致，不回显凭据或原始上游响应。

实现后执行类型检查、构建及全量离线回归。在线公开匿名查询、人工登录/取消、本人只读验证分别记录；真实写入仍需具体对象和操作范围的单独授权。

初次诊断轮次只做故障核对、公开匿名网络复测和方案文档，没有修改生产代码或用户配置。后续自动代理开发已完成类型检查、构建及137项全量离线测试，本机自动代理公开搜索成功；没有真实模型请求、登录或账户写入。自动代理验收不代表上述登录引导和模型同轮停止策略已经实现。
