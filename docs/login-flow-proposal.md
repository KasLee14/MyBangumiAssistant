# `/login` 流程调整建议

- 日期：2026-10-02
- 状态：用户已确认仅实施 OAuth 主登录，条目取消收藏暂停。OAuth回调/Token认证及离线验证已落实；第4节专用网页登录与第6节独立Cookie桥接属于历史提案，不再作为当前实施要求，未采集Cookie或安装扩展。
- 关联：[设计文档](development-plan.md)、[开发规划](development-roadmap.md)。

## 1. 当前网络与卡住原因

以下网络及旧流程记录保留为调查证据；当前实现已切换为 OAuth 主登录，实施情况见第7节。

当前构建读取的有效代理已为 `http://127.0.0.1:7890`。2026-10-02 使用应用同类 undici 请求封装进行无凭据复测：

| 地址 | 结果 | 耗时与边界 |
| --- | --- | --- |
| `https://bgm.tv/login` | HTTP 200 | 约0.49秒，网页登录地址可达；没有输入密码或取得账户凭据 |
| `https://next.bgm.tv/p1/me` | HTTP 401 | 约0.51秒；匿名请求的预期认证响应，证明API可达，不是用户登录失效的证据 |

显式 Clash 对照同样返回200/401，约0.50秒。进一步使用生产 `WebTransport` 和实际代理策略验证：代理来源为应用环境变量，两个官方主机均选择Clash，p1匿名请求约0.51秒返回401。连通性在当前新启动配置下恢复；正在运行的旧chat是否采用该配置、真实Cookie是否能完成握手，尚未验证。没有修改代理配置、读取真实Cookie、执行认证或账户写入。

当前登录每1.5秒读取专用浏览器的Cookie；有传统认证Cookie后，串行核对 `/p1/me` 与传统网页账户。多数核实异常被隐藏后重新进入循环，所以网络失败仍显示“已取得网页会话，正在核对”，一直等待到总超时。Cookie等待与账户核实失败没有明确分开，是本次需要调整的流程问题。

## 2. API授权与网页Cookie的区别

核对官方公开文档及服务端源码：

- [OAuth说明](https://github.com/bangumi/api/blob/master/docs-raw/How-to-Auth.md)：浏览器授权返回code，应用换取Access Token/Refresh Token，供API请求使用；需要注册应用和配置回调。OAuth响应本身不提供传统网页Cookie。
- [p1登录实现](https://github.com/bangumi/server-private/blob/master/routes/private/routes/auth.ts)：邮箱、密码及Turnstile令牌提交一次登录请求，成功返回用户并设置新会话。令牌获取仍可能需要浏览器验证。
- [会话类型](https://github.com/bangumi/server-private/blob/master/lib/auth/session.ts)：新会话为 `chiiNextSessionID`，传统网页为 `chii_auth`。未找到可据以实现的新会话兑换传统网页Cookie的公开支持入口，不承诺二者互换。
- [现有删除能力说明](collection-delete-capabilities.md)：本项目条目收藏删除仍依赖传统网页Cookie/UA及动态令牌。纯Token或新会话登录不能直接替代此认证；相关源码事实不是线上兼容验收。

如果应用自己控制OAuth浏览器并另外获取其网页Cookie，是额外的Cookie获取步骤，不能描述为OAuth接口自动同步Cookie。

## 3. 方案比较

| 方案 | 体验与能力 | 代价 |
| --- | --- | --- |
| A：统一网页登录，成功事件触发一次握手 | 先前建议，用户更偏好B；保留目前全部读写及删除认证，一次网页登录；去掉固定Cookie轮询及重复核实 | 仍需应用专用浏览器手动登录；必须真实验证登录成功事件和Cookie/UA兼容 |
| B：OAuth回调作为主要API登录 | 用户已选择的主方向；使用日常浏览器已登录状态授权，回调完成API认证，Token可刷新 | 注册应用、回调与Token保护；网页删除另需Cookie认证，具体获取方式尚未选定 |
| C：直接p1 API登录 | 帐密及Turnstile通过后，一次请求取得新会话 | 新增独立密码输入与验证码流程，仍不能直接保证传统网页删除；不建议为本轮改善引入双认证 |

若用户更重视“使用已有浏览器账号并点击授权返回”，可选择B，但要接受API登录与网页操作登录分开；不能让卡片的“已登录”掩盖删除尚未认证。

## 4. 先前A方案的交互（供比较）

1. `/login` 首先使用现有统一代理策略进行有界连接/认证核实。网络不可达直接提示失败原因和代理来源，不打开浏览器或反复重试；现有登录有效则快速返回“已登录，当前用户：ID”。本机无有效认证才进入网页登录。`/login --force` 明确重新登录或换账号。
2. 打开应用专用网页登录窗口，提前监听主页面导航完成及固定官方主机的登录响应事件。事件只触发本地Cookie检查，不读取或记录用户提交的密码，不记录响应Cookie值。
3. 登录响应处理完成/已登录页面加载完成后读取必要Cookie和匹配UA，避免在浏览器处理Set-Cookie前读取。用串行状态机避免多个事件重复启动核实；不每1.5秒扫描。增加“已完成网页登录，立即核实”的手动入口，作为事件识别失败的后备；取消、关闭和总超时均可结束等待。
4. Cookie就绪后，只启动一轮网页/API账户核实，每个请求上限约8秒，并传递取消信号。失败显示具体安全类别：API连接超时、网页连接失败、认证拒绝、账户不一致等；不把所有错误改写为“继续等待”。网络失败允许用户明确重试核实，复用当前专用窗口内的候选Cookie，不要求重新输入密码；重复认证拒绝则提示重新登录。候选只保留在本次内存，不当作已保存登录。
5. 两侧账户一致后原子保存DPAPI保护的必要Cookie/UA，关闭专用窗口，立即更新用户ID。失败/取消保留原已保存认证，不自动重放此前修改或继承旧授权。

建议状态文案按阶段切换：

```text
检查现有登录…
请在浏览器完成登录（Esc 取消）
网页已登录，正在核实API账户…
登录成功，当前用户：<ID>
```

失败示例：

```text
网页已登录，但API账户核实连接超时。
当前代理：<实际代理来源与地址>
本次尚未保存新登录。可重试核实或取消，不会自动重复登录。
```

## 5. 实施及验收边界

用户已选B，Cookie补充方式选定后再改生产代码；不能把先前A的建议当作已授权实施方案。OAuth先实现注册应用配置、受限回调、Token保护/刷新、API适配和独立状态；补充认证随后以既有Cookie核实/删除链路接入。无需Cookie即可完成OAuth登录。

离线用例应覆盖：多事件只核实一次、Cookie晚于导航事件写入、未登录页面不误判、网络失败不循环、取消与关闭、已有登录快返、换账户旧授权失效、失败保留原认证、输出不含密码/Cookie。再做真实专用网页登录与账户只读握手；真实写入/删除仍按具体对象和操作范围单独验收。

本轮只检查源码、官方公开认证资料及匿名网络，不改登录生产代码；未运行新实现的类型检查/离线回归，现有测试数字属于此前验收。

## 6. 历史讨论：OAuth主登录加可选Cookie认证（补充认证暂缓）

### 6.1 核心行为

- `/login` 在默认日常浏览器打开官方OAuth授权页，使用注册的回调和随机state接收code、换取Token，只读核对数字账户后保存API认证，即刻返回。无需等待Cookie，浏览器已有本站登录时可直接授权；实际回调地址支持仍须注册/联调，不先承诺任意端口可用。
- 查询、个人收藏、评分、标签、短评及原生进度改用API Token。服务端[认证中间件](https://github.com/bangumi/server-private/blob/master/routes/hooks/pre-handler.ts)支持Bearer，可考虑保留现有p1数据转换，通过适配层切换认证；必须逐能力核实兼容，不直接把Mock视为线上通过。
- 传统网页删除仅使用Cookie/UA，首次删除前若缺少有效网页认证，引导补充；Cookie失效只暂停删除，不使API登录失效或阻止其他API能力。
- OAuth完成页可提供“同时启用网页删除”入口，也允许稍后用建议命令 `/login --web` 补充。选择补充失败仍保留已经成功的OAuth登录；不将本次主动认证视为自动执行删除的授权。

### 6.2 复用日常浏览器Cookie的桥接

OAuth服务不会在回调中发送传统Cookie。Cookie按站点作用域发送，localhost回调网页不能直接读取另一站点Cookie，HttpOnly也不能通过普通页面脚本读取；见[Cookie说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)。要保留日常浏览器现有登录，又避免复制粘贴或专用窗口重复登录，建议增加用户主动授权的小型Edge/Chrome扩展及本机桥接：

1. 一次性安装扩展和本机Native Messaging桥接。扩展Cookie权限限定固定Bangumi域名，首期只处理 `bgm.tv` 与必要Cookie白名单，不枚举或导出其他网站/浏览器档案。用户主动点击“启用网页删除认证”才同步；不做后台定时Cookie采集。
2. 通过[浏览器Cookie API](https://developer.chrome.com/docs/extensions/reference/api/cookies)取得必要Cookie及匹配UA，绑定用户选择的浏览器账户档案。此为明确授权的桥接方案，当前不会直接读取浏览器Cookie数据库或解密日常浏览器存储。
3. 通过[Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)传给固定本机宿主；只接受指定扩展及固定认证消息，绑定本次短时请求，拒绝任意文件路径/命令。Cookie不放URL、剪贴板、聊天或日志，不发送到第三方服务。
4. 宿主只读核实网页账户与当前OAuth数字账户相同。核实Cookie时不得同时发送Bearer，否则API可能优先接受Token而掩盖Cookie无效。匹配且有效后才DPAPI原子保存；错配/失败保留原凭据并禁用新Cookie，不允许跨账户混用。
5. 通过本地事件通知chat“网页删除认证已就绪”，不固定轮询Cookie或失败后重复账户请求。同步失败明确说明原因，让用户主动重试；Cookie过期再次主动同步。

扩展是新增安装成本，并会新增用户明确授权的日常浏览器Cookie桥接能力；原AGENTS禁止直接读取日常浏览器凭据的约束仍适用于当前实现。若选定此方案，应更新约束以仅允许固定域名、主动授权的扩展桥接，不将它扩大为任意浏览器凭据读取授权。本轮不安装、注册或读取任何真实Cookie。

如果不希望安装扩展，保留OAuth主登录，第一次需要网页删除时另开专用网页登录窗口，以登录成功事件取得Cookie。这会增加一次独立登录，但仍不会阻塞普通OAuth登录。OAuth自己控制专用浏览器同时取得Token和Cookie的方案可以减少桥接安装，却不能保证复用日常浏览器已有会话，因此不作为当前偏好的默认方式。

### 6.3 状态与账户绑定

```text
当前Bangumi用户：<username>
API授权：已登录
网页删除认证：已就绪 / 未启用 / 已失效 / 待核实
```

Token与Cookie分别保存有效期与验证状态，统一绑定数字账户ID。切换OAuth账户立即使旧网页认证对新账户不可用并清除旧预览授权；同账户Token刷新不会无故删除有效Cookie。状态查看不等待网页认证完成，顶栏账户以API核实结果为准。

### 6.4 需要在实施时核实的条件

- 注册应用Client ID、Client Secret及实际可接受的回调地址；不复用第三方App的应用秘密，不要求用户把秘密贴到聊天中。
- OAuth配置与Token本地保护、state一次性校验、回调超时/拒绝、刷新失败；桌面应用发布方式与长期应用秘密处理单独落实，不承诺源码中的共享secret可以保密。
- p1各现有能力的Bearer兼容、数字账户绑定、Cookie单独核实、浏览器档案及UA一致、扩展安装/卸载与桥接验证；离线用例后再单独做用户授权的真实OAuth及网页认证只读验收。
- 真实删除仍须明确对象、具体预览确认及网站回读。扩展只同步认证，不开放删除、任意网页请求或shell执行能力。

本次为官方源码及浏览器能力的只读研究和方案更新，没有实现OAuth/扩展、读取真实浏览器凭据或执行账户写入。

## 7. 当前已选择与实施：仅 OAuth 主登录

用户决定先实施 OAuth，条目取消收藏不开放。`/login`/`login --force`打开默认日常浏览器，OAuth授权回环回调到固定127.0.0.1端口；随机state、路径和单次code校验通过后立即交换Token，只读核对数字账户再DPAPI保存。API桥接改用Bearer；到期前可刷新并核实同账户，不重复业务写入。详细登记、环境变量引用和回调配置见[README](../README.md#bangumi-认证与进度限制)。

删除工具、旧CLI、宿主计划、执行器和实际worker均阻止条目取消收藏；旧网页登录Cookie文件不读取、不迁移、不自动删除。不开发扩展或Native Messaging，本轮不读取日常浏览器Cookie。已做本地回调、模拟OAuth/账户、实际DPAPI假凭据与桥接假网络验证；真实应用授权、账户读取及写入尚未执行。最终检查数量以[开发规划](development-roadmap.md)为准。
